# **Функциональная спецификация фич: Сервис карточек (MVP и Post-MVP)**

В данном документе приведено расширенное техническое и продуктовое описание функционала сервиса карточек на основе утвержденных бизнес-требований. Документ служит единым источником правды для разработки MVP.

## **1\. Аккаунты и разграничение доступа**

| Фича | Статус | Подробное описание и ограничения |
| :---- | :---- | :---- |
| **Семейные аккаунты** | MVP | В системе жестко заложено 4 аккаунта (для каждого члена семьи). Создание аккаунтов происходит на уровне миграций БД (Flyway). Отдельного UI для регистрации в MVP нет. Изоляция данных (Multi-tenant) реализуется по owner\_id. |
| **Сброс пароля** | MVP | Отсутствует UI для восстановления. Сброс пароля осуществляется администратором (Tech Lead) вручную через прямой UPDATE хеша пароля в базе данных. |
| **Ролевая модель** | Post-MVP | Иерархия «Учитель — Ученик» отложена. В MVP все 4 аккаунта имеют равнозначные права (Owner своих данных). |

## **2\. Организация наборов и карточек**

> * **Вложенность папок (MVP):** Максимальная глубина вложенности папок ограничена 2 уровнями (Папка \-\> Подпапка) для предотвращения сложных рекурсивных запросов к БД на старте.  
> * **Связь Папок и Наборов (MVP):** Реализуется связь «Один ко многим» (1:N). Один набор (Deck) жестко принадлежит только одной папке. Если требуется семантически связать набор с другими категориями, используются **Теги**.  
> * **Управление (MVP):** Полный CRUD для папок и наборов внутри них.

## **3\. Содержимое карточек (Rich Flashcards)**

Карточка является базовой единицей заучивания и поддерживает полиморфную структуру дополнительных атрибутов.

| Атрибут | Правила и ограничения (MVP) |
| :---- | :---- |
| **Лицевая и обратная сторона** | Жесткое ограничение длины текста — до 500 символов (достаточно для одного сложного предложения или фразы, но защищает от загрузки больших текстов). |
| **Доп. грамматические поля** | В БД хранятся в формате JSONB, однако на уровне API/UI фиксируется жесткий DTO с заданными полями (примеры, приставки, формы), чтобы упростить разработку фронтенда в MVP. |
| **Примеры предложений** | Выделены в отдельное текстовое поле (ограничение до 1000 символов). |
| **Тегирование** | В MVP реализована только возможность назначить тег карточке. Поиск, фильтрация по тегам и сборка динамических колод по тегам перенесены в Post-MVP. |

## **4\. Механика режима обучения (Learning Engine)**

Ядро системы, отвечающее за тренировку и алгоритмическую выдачу карточек.

> * **Старт сессии:** Пользователь выбирает направление перевода перед стартом. Это исключает необходимость в сложных "Smart Reverse Cards" на этапе MVP — направление фиксируется на весь раунд обучения.  
> * **Multiple Choice (Батчи по 10):** Выбор из 4 вариантов ответа. Если в папке не хватает карточек для генерации 3 дистракторов, система добивает пустые слоты случайными карточками *из других наборов с совпадающими языками оригинала и перевода*. (Умный подбор похожих дистракторов — Post-MVP).  
> * **Writing Mode (Письменный ввод):** Жесткая валидация. Ответ засчитывается как верный при 100% совпадении букв, однако алгоритм проверки **игнорирует**: регистр (case-insensitive), знаки препинания и лишние/двойные пробелы.  
> * **Озвучка (Web API TTS):** В MVP интегрируется бесплатный Web Speech API на стороне фронтенда для произношения слов (без хранения аудиофайлов на бэкенде).

## **5\. Импорт и загрузка наборов**

Для быстрого старта реализован массовый импорт. В MVP импорт происходит **без проверки на дубликаты** (полный insert). Для защиты системы от перегрузки (DDoS-ошибок пользователя) вводится лимит: **максимум 200 карточек в одной загрузке/файле**. Экспорт данных в файл отложен в Post-MVP.

## **6\. Резервное копирование и надежность**

Автоматический бэкап данных (Data Portability) реализован на инфраструктурном уровне системы (дампы PostgreSQL). Пользовательский экспорт/импорт прогресса в UI не входит в MVP.
