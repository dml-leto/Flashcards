# FC-1 · Процесс работы

- **Статус:** Accepted
- **Дата:** 2026-10-01
- **Issue:** FC-1

## Контекст
Проект ведёт один разработчик (бэкенд) вместе с Claude (PM, архитектор, ментор, фронтенд). Задачи живут в GitHub
(issues, milestones, Projects #5). Обсуждение прошло в сессиях 2026-09-30 – 2026-10-01. Поводы для решения:
- статус-сводки предлагали «параллельные» варианты работы, хотя разработчик один;
- в задачах смешивались шаги работы и нерешённые вопросы с trade-offs;
- `Closes #N` в PR закрывал issue при merge, и задача уезжала в `Done` без проверки DoD;
- все продуктовые решения висели в milestone `00`, хотя большинство из них нужны только на поздних этапах.

## Решение

### Последовательная работа
- Задачи выполняются строго по одной. В `In Progress` всегда одна задача.
- Если задача заблокирована, она уходит из `In Progress`, и берётся следующая.
- Claude всегда называет одну следующую задачу: с наивысшим приоритетом среди незаблокированных.
  В `In Progress` её переводит пользователь, когда реально начинает работу.
- Пользователь может взять другую задачу вперёд. Claude тогда высказывает своё мнение, но следует решению.

### Поток статусов
| Статус | Значение | Кто переводит |
|---|---|---|
| `Backlog` | Задача не готова: не описаны шаги или есть открытые блокеры | Claude при создании |
| `Todo` | Готова к работе (Definition of Ready, см. ниже) | Claude после grooming |
| `In Progress` | В работе (одна задача) | Пользователь |
| `In Review` | Открыт PR с `Closes #N` | Workflow доски автоматически |
| `Done` | Claude провёл ревью и проверил DoD, вердикт «сделано» | Пользователь или Claude по согласованию — закрытием issue |

- **Auto-close при merge выключен** в настройках репозитория (Settings → General → Issues →
  «Auto-close issues with merged linked pull requests»). Поэтому в PR пишем `Closes #N`: ключевое слово только связывает
  PR с issue (и включает переход в `In Review`), но не закрывает issue.
  Это заменяет решение от 2026-09-30 писать `Refs #N`: `Refs` не связывает PR с issue, и переход в `In Review` не срабатывал.
- Workflow доски `Item closed → Done` оставлен: issue закрывает только человек, workflow лишь синхронизирует колонку.
- Если вердикт ревью «не сделано», задача возвращается в `In Progress` с комментарием, что осталось.

### Definition of Ready (условия перехода в `Todo`)
1. Шаги описаны так, что по ним понятно, что делать.
2. DoD проверяемый.
3. Все блокеры (`blocked by`) закрыты.
4. Если результат — документ, путь к нему указан.

### Типы задач
- **`type:decision`** — задача на проработку. В ней: 2–4 вопроса, что хотим получить на выходе, путь к документу-результату,
  предварительные мысли о подходах и технологиях. Если было предварительное обсуждение, в задаче упоминание о нём,
  а саммари — в документе-результате. Trade-offs в задачу не пишем, они появляются в документе.
  Если вопросов больше четырёх, задачу дробим и связываем.
- **`type:development`** — задача на разработку: шаги, при необходимости ключевые моменты «как», DoD.
  Если «что» или «как» зависит от нерешённого вопроса, задача заблокирована соответствующей `decision`-задачей.
- Остаются `type:bug` и `type:tech-debt`. Метки `type:task` и `type:feature` заменены на `type:development`.
- Глубина детализации задач подбирается итеративно по ходу работы.

### Сквозные идентификаторы
- ID задачи = `FC-<номер issue>`. Отдельного счётчика нет: номер уникален и известен сразу после создания issue.
- Заголовок issue: `FC-17 · Название`. Ветка: `feat/FC-17-gradle-settings`. Заголовок PR / squash-коммита:
  `build: add Gradle settings (FC-17)` в формате Conventional Commits.
- Документы-результаты: `docs/decisions/fc-<N>-<slug>.md`, для ADR — `fc-<N>-adr-<slug>.md`.
  Отдельная нумерация ADR не используется, порядок принятия виден по дате в индексе.
- В репозитории включён Autolink `FC-` → issue (Settings → Integrations → Autolink references).
- Если по ходу задачи появился документ, которого не было в плане, путь к нему добавляется комментарием к issue.

### Планирование milestones
- Решения лежат в том milestone, который они блокируют, и берутся перед стартом этого этапа, а не все заранее.
- Порядок этапов и зависимости между ними описаны в начале описания каждого milestone («Зависит от: …»).
- Rolling-wave planning: детализированы до задач только текущий и следующий этап.

## Рассмотренные альтернативы
- **`Refs #N` вместо `Closes #N`:** не создаёт связь PR ↔ issue, и `In Review` не выставляется автоматически.
- **Отдельный статус «Needs refinement»:** избыточен. `Backlog` + `blocked by` + Definition of Ready дают то же самое,
  а GitHub сам помечает заблокированные карточки значком Blocked.
- **Ручная нумерация ADR (`0003-…`) рядом с FC-ID:** два идентификатора одного решения. Порядок и так виден по дате.
- **Отдельные папки `docs/adr/` и `docs/decisions/`:** два индекса, и не всегда ясно, куда класть решение.

## Последствия
- Каждая задача получает понятный момент закрытия, и ни одна не попадает в `Done` без ревью.
- Claude поддерживает в актуальном состоянии: статусы `Backlog`/`Todo`, блокеры, индекс решений.
- `CLAUDE.md` содержит только постоянные правила. Текущий статус смотрим на доске, план — в milestones,
  историю решений — здесь.
