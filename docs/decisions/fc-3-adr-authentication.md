# FC-3 · ADR: Аутентификация: серверная сессия (Spring Session JDBC) + HttpOnly cookie

- **Статус:** Accepted
- **Дата:** 2026-09-26
- **Issue:** FC-3 ([#3](https://github.com/dml-leto/Flashcards/issues/3))

## Контекст
- Клиент: браузерная SPA на том же origin (FC-2). 4 пользователя, один инстанс приложения, одна БД PostgreSQL.
- Регистрации нет, сброс пароля делает администратор вручную в БД. После сброса старый вход должен сразу перестать работать.
- В будущем появятся машинные клиенты: MCP-сервер (эпик CARD-4) и, возможно, мобильное приложение или публичное API.

## Решение
- **Веб:** серверная сессия, хранилище — **Spring Session JDBC** (таблицы создаются миграцией Flyway,
  а не автоинициализацией). Сессии переживают рестарт приложения.
- **Cookie сессии:** `HttpOnly; Secure; SameSite=Lax; Path=/`.
- **CSRF:** включён. Токен для SPA выдаётся в SPA-режиме Spring Security: фронтенд читает cookie `XSRF-TOKEN`
  и отправляет заголовок `X-XSRF-TOKEN` (точную конфигурацию сверить с документацией Spring Security 7 при реализации).
- **Пароли:** `DelegatingPasswordEncoder` (bcrypt или Argon2), с возможностью сменить алгоритм без миграции хешей.
- **Защита входа:** ограничение частоты попыток логина, смена ID сессии при входе (защита от session fixation,
  включена в Spring по умолчанию), logout инвалидирует сессию.
- **Время жизни:** долгий idle-timeout, удобный для семьи. Конкретное значение выбирается на Этапе 2.
- **Будущие машинные клиенты:** отдельная `SecurityFilterChain` на `/mcp/**` (и `/api/public/**`, если появится)
  как OAuth 2.1 resource server с bearer-токенами (JWT). Веб-цепочка при этом не меняется.

## Рассмотренные альтернативы
- **JWT access + refresh (stateless):** основное преимущество (нет хранилища сессий) при нашем профиле нулевое:
  каждый запрос и так идёт в PostgreSQL. Корректная ротация refresh-токенов с обнаружением повторного использования
  всё равно требует состояния в БД. Access-токен нельзя мгновенно отозвать. В `localStorage` токен уязвим к XSS,
  а JWT в HttpOnly cookie — это переизобретённая сессия с большим payload и без отзыва.
- **OAuth 2.0 / OIDC с внешним провайдером:** не нужен для входа по логину и паролю в собственное приложение.
  Вернуться к нему при публичной регистрации («Войти через Google»), где после входа веб всё равно держится на сессии.

## Последствия
- Мгновенный отзыв доступа: удаление строк из таблиц сессий.
- Фронтенд обязан корректно работать с CSRF-токеном и обрабатывать 401 (редирект на логин).
- Нужен тот же origin для фронта и API (закреплено в FC-2).
- Горизонтальное масштабирование не требует доработок: хранилище сессий уже общее (БД).
- Открытый вопрос, вынесенный в отдельную задачу Этапа 2: как завести 4 аккаунта, не положив пароли и хеши в публичный git.
