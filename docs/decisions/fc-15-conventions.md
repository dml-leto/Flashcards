# FC-15 · Где живут правила, метки, коммиты и шаблоны

**Статус:** accepted · **Дата:** 2026-10-01 · уточняет FC-1

**Правила живут только в `CLAUDE.md`, решения хранят только «почему».** Правило из FC-1 («следующая задача — с наивысшим
приоритетом») устарело после FC-32, но продолжало лежать в документе решения: две копии правил расходятся.
Поэтому действующее правило меняется правкой `CLAUDE.md` через PR, а документ решения не редактируется, кроме статуса.
Форматы, которые лежат в репозитории файлом (шаблоны issue и PR), не пересказываются: источник правды — сам файл.
Так устроены handbook-first в GitLab, RFC/Reference в Rust и `CLAUDE.md` + короткие ADR в mattpocock/skills.

**Метки `type:*` + `area:*`, стандартные метки GitHub удалены.** У задачи два измерения: тип и область.
Стандартные метки описывают только одно (`bug`, `enhancement`), для `decision` и `tech-debt` аналогов нет,
а `documentation` смешивает тип с областью. Метки с префиксами — тот же приём, что `kind/*` и `area/*` в Kubernetes.
Нативные Issue Types GitHub доступны только организациям.

**Стандартные типы Conventional Commits, без scope.** Переименовать `feat` → `feature` или `chore` → `other` можно,
но тогда changelog/semver-инструменты (release-please, commitlint) перестают понимать историю. Scope не нужен:
область видна по метке `area:*` в issue, на которое ссылается `FC-N`.

**Шаблоны issue — в Markdown, без YAML issue forms; `CONTRIBUTING.md` не создаём.** Почти все issues создаются через
`gh --body`, где шаблоны не работают, а Markdown даёт тот же текст, что и ручное создание. Issues и PR создают только
collaborators, поэтому отдельный гайд для внешних контрибьюторов стал бы третьей копией правил.
